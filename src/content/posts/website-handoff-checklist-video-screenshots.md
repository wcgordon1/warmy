## Key Takeaways

- **Record ownership separately from instructions.** A video cannot transfer a domain or billing account. Name the owner of each service in a written record.
- **Teach tasks the client will repeat.** Start with ordinary content changes and the publication process. Leave internal development detail out unless the client needs it.
- **Use video for sequences and screenshots for reference.** A clip can show an action. A labeled screenshot can make a particular control easier to find later.
- **Give the client one maintained index.** Link each task, access responsibility, and support route from the same document. Scattered chat attachments are difficult to maintain.
- **Verify the delivered experience.** Open the files and links with the intended access level. A successful export does not prove that the client can use the handoff.

## What a website handoff actually includes

A website handoff transfers usable knowledge and confirms operational responsibilities. It tells the client which site was delivered, which tasks they can perform, who owns the connected services, and how maintenance and support work.

A project launch announcement serves a different purpose. It marks the site going live. It does not explain domain renewal, user access, backups, form destinations, or who handles later changes. Those responsibilities need a clear record.

A handoff also differs from a source-code archive. A client may need the code, repository access, or build instructions under the project agreement. They may also need a simple way to update a staff profile without understanding the development stack. Document both needs at the appropriate level.

Agree on the handoff scope before the final meeting. Separate outstanding work from completed deliverables. If a feature or integration remains provisional, label it clearly and name the next decision. Do not use a polished walkthrough to imply that unfinished behavior has shipped.

## How We Chose the Handoff Checklist

This checklist uses four practical acceptance questions. Is the service owner named? Can the intended user reach the task? Does the instruction show completion? Is there a maintained support route?

The examples below are editorial templates. The product discussion uses public Toads and Screen Index documentation reviewed October 23, 2026. We did not measure support-ticket reduction, client learning speed, or task success across a user study.

## Step 1: Write the ownership and access record

Create a list of the services the website depends on. Include the domain registrar, hosting, repository, content system, email or form destination, and any other configured services in scope. Record the owner and renewal responsibility for each one.

Keep credentials in the agreed secure process. A handoff document should explain how access is granted and managed rather than publishing passwords or recovery codes. Record whether the client has accepted the appropriate invitation and can reach the intended workspace.

Separate access from authority. A person who can edit content may not own billing or be able to change account administrators. Name the appropriate contact for those actions so a later renewal or staffing change does not become a guessing exercise.

Confirm the source of truth. If the public site is built from a repository, identify that repository and its production branch in the technical handoff. If a managed editor owns content, explain where the client should make changes. Do not give competing instructions for the same page.

## Step 2: Choose the first tasks to teach

Start with the work the client agreed to maintain. Examples include editing contact details, updating a service description, publishing a post, or replacing an approved image. Each task needs a starting point and a visible completion state.

Explain permissions and review requirements before the action. If an editor can save a draft but another person publishes it, show that boundary. A tutorial that assumes administrator access may fail for the person who actually receives it.

Keep tasks separate when their risks differ. Changing body copy, changing a payment setting, and replacing a form destination are not the same operation. Teach the ordinary content workflow and route consequential configuration changes to the appropriate owner.

## Step 3: Record short walkthroughs on Mac

Plan the task before opening the recorder. Use approved example content, remove unrelated windows, and make the interface readable. Say what the viewer will complete before showing the first click.

[Toads](https://toads.io/) documents a native Mac recording and editing workflow. Its timeline and caption tools can help prepare a walkthrough before export. Its MCP connection is relevant if your team already uses an editing agent, but the team still needs to review the result.

Cut setup that the client does not need. Keep warnings or required conditions next to the action they affect. Watch the final file and check the captions against what the interface shows. Then store the approved version in the agreed delivery location.

## Step 4: Select screenshots that answer a question

Use a screenshot when the client needs a quick reference to a control, result, or interface state. Give it enough surrounding context to be recognizable. Label the image according to the task rather than using a filename full of capture timestamps alone.

[Screen Index](https://screenindex.app/) documents searching screenshots by visible text and other context, then opening, copying, or editing the result. That can help when the image you need is already in a larger project library. Keep the [redesign screenshot checklist](/posts/website-redesign-screenshot-checklist-mac/) for the evidence you need to retain internally.

Prepare a separate shareable copy when the source image contains internal details. Inspect the export and its destination before sharing. Keep private notes, unrelated browser tabs, and credentials out of the client reference material.

## Step 5: Verify delivery and record acceptance

Open the maintained index and every linked deliverable. Check the files with the access level the recipient will use. A link that works in the agency owner’s account may fail for the client.

Record which tasks were demonstrated, which responsibilities were accepted, and which questions remain open. Do not call the project fully handed over when a required owner cannot access a service or a promised feature still fails.

Finish with a maintenance note. Name the owner of future documentation updates and explain when a new interface requires new screenshots or video. The handoff becomes less useful when the site changes but the instructions do not.

## An illustrative handoff package

A small service website could have one index document, an ownership record, and separate walkthroughs for its routine editing tasks. Each walkthrough links to the relevant administration page and a reviewed reference image when useful.

That package is an example of organization, not a claim that a fixed number of videos fits every site. Start with the client’s actual responsibilities. Add detail when it helps them perform or route a real task.
