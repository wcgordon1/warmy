## Key Takeaways

- **Capture a repeatable set of views.** A before-and-after comparison needs the same page, width, and state. Otherwise the screenshots answer different questions.
- **Keep context with the file.** Record the page URL, capture date, and review status in the project notes. A screenshot alone may not reveal which build it shows.
- **Separate visual evidence from functional checks.** An image can show a label or layout. It cannot prove that a form submits or that keyboard focus works.
- **Search by the clue you remember.** Screen Index documents text, source context, and other search inputs. These tools help retrieve evidence without requiring a perfect filename.
- **Review the copy you share.** Crop or cover private details where needed, then inspect the exported image. Keep internal source files separate from approved client material.

## What a redesign screenshot checklist actually is

A screenshot checklist defines the evidence a review needs. It tells the team which page, viewport, and interface state to capture. It also explains how to identify the resulting files and connect them to a decision.

A mood board is different. It collects design references and possible directions. A redesign evidence library records the site being changed and the result being reviewed. Mixing those collections makes it easier to mistake a reference for an implemented screen.

The checklist is also different from automated visual regression testing. A manual screenshot review can be useful for a bounded project, but it does not run on every deployment. If a project needs automated regression coverage, choose that testing approach separately.

Use screenshots to support a clear question. “Is the primary action readable at the narrow width?” is reviewable. “Does the site feel better?” needs a more specific brief. The capture should preserve enough context for another person to understand what is being evaluated.

## How We Chose the Review Criteria

This checklist uses four observable criteria: a stable page URL, a recorded viewport width, a named interface state, and a version or date. Together, those fields make it possible to reproduce the view and compare the right images.

The Screen Index discussion is based on its public product page reviewed October 23, 2026. We did not measure retrieval speed, OCR accuracy, or review completion time. The workflow does not depend on achieving a particular search result in every screenshot.

## Build the capture list before redesign work starts

Choose the pages that carry the project’s main tasks. That might include the home page, a service page, a contact flow, and an important article or product page. Write the reason for each capture so the list does not become a collection of unrelated pictures.

For every page, choose the wide and narrow views the team will review. Record the actual width. Do not label two screenshots “mobile” when one uses a different viewport and shows a different layout.

Include meaningful interface states. A form’s empty screen is different from its validation message or successful submission screen. Capture an approved test environment when showing data entry and results. Never use private customer information as convenient demonstration content.

Keep the original “before” captures. A later change to the live site should not overwrite the evidence that informed an earlier decision. Save revised images with an identifiable date or version rather than replacing the reference silently.

## Organize the files so the review can continue next week

A simple folder structure is enough to start: project, review date, then before or after. Use a consistent filename that identifies the page, width, and state. The point is to make the file understandable outside the conversation where it was created.

Add a small decision log. For each issue, link the relevant image and name the expected change. Mark whether the issue is open, ready to verify, or accepted. A screenshot library becomes useful when it connects observations to decisions.

## Prepare a screenshot for client review

Start with the internal evidence file. Make a shareable copy and remove information the client does not need. Screen Index documents crop, annotation, and privacy tools, but the final responsibility is to inspect what you export.

Use an arrow or short label only when it clarifies the issue. Keep enough of the interface visible to show where the problem occurs. An extreme crop can make a clear observation difficult to reproduce.

Store the reviewed copy in the project’s delivery location. The file being local to your Mac does not make the delivery location private. Check access separately before sharing the link.

## An illustrative redesign review

Imagine a service page whose contact action disappears below a long introduction at a narrow width. Capture the original view and the revised version at the same width. Add a note describing the intended action and what changed.

Then open the revised page and follow the action. Inspect keyboard focus and any resulting form states. The screenshots support the review, while those live checks establish whether the interaction works. This example illustrates a process and does not report a measured conversion change.
